# Supabase by hand

**Use this when** you cannot run `npx mushi-mushi selfhost up` (a locked-down CI, no Node), or you want to know exactly what it did. The [quickstart](/self-hosting) does all of this in one command; `selfhost up --print-commands` prints this same sequence with your values filled in.

<Callout type="info">
  Run every `supabase` command from `packages/server/`. The CLI looks for `supabase/` under the current directory; from the repo root it fails with "entrypoint path does not exist".
</Callout>

## 1. Link and push the migrations

```bash
cd packages/server
supabase login
supabase link --project-ref <your-ref>
supabase db push --remote      # CLI 2.x: --linked. Without either, CLI 3.x pushes to your LOCAL database
```

The migrations enable the extensions they need (`vector`, `pgcrypto`, `pg_cron`, `pg_net`, `citext`; `age` when available). Vault is part of every Supabase project.

## 2. Set the function secrets

Generate one secret and keep it: the same value goes into the database in step 3.

```bash
openssl rand -hex 32
```

```bash
cat > mushi-secrets.env <<'EOF'
MUSHI_INTERNAL_CALLER_SECRET=<the secret>
MUSHI_INSTANCE_MODE=self-hosted
ADMIN_BASE_URL=https://mushi.example.com
MUSHI_ADMIN_ORIGIN_ALLOWLIST=https://mushi.example.com
ANTHROPIC_API_KEY=sk-ant-...
EOF
supabase secrets set --env-file mushi-secrets.env && rm mushi-secrets.env
```

`ADMIN_BASE_URL` is your console's address: links in Slack, Discord and email, and the `mushi login` approval page, open it. `MUSHI_ADMIN_ORIGIN_ALLOWLIST` lets the console's browser calls through (CORS); the built-in list covers only Mushi Mushi Cloud and `http://localhost:6464`-style dev ports. The AI key is optional; `OPENAI_API_KEY` works instead. Every other secret is on [Environment variables](/self-hosting/environment).

## 3. Point cron at your project

**`db push` alone is not enough.** The migrations seed `mushi_runtime_config.supabase_url` with Mushi Mushi Cloud's URL and leave the two tokens empty, so until you overwrite them every pg_cron job calls Mushi Mushi Cloud, or fails. New orgs also land on a Cloud plan row (300 diagnoses a month, 3 apps, 1 seat), which means nothing on your own instance.

```bash
cat > mushi-runtime-config.sql <<'EOF'
insert into public.mushi_runtime_config (key, value) values
  ('supabase_url', 'https://<your-ref>.supabase.co'),
  ('service_role_key', '<the secret>'),
  ('internal_caller_token', '<the secret>')
on conflict (key) do update set value = excluded.value, updated_at = now();
EOF
supabase db query --remote --file mushi-runtime-config.sql && rm mushi-runtime-config.sql
```

`mushi.edge_function_post` (every cron job) reads `supabase_url` and `service_role_key`; pipeline recovery reads `internal_caller_token`. To also lift the plan limits, run the full file `selfhost up --print-commands` prints: it adds an `update public.pricing_plans …` and makes sure the private `screenshots` bucket exists.

## 4. Deploy the functions

```bash
supabase functions deploy       # every function; verify_jwt comes from supabase/config.toml
```

A plain deploy leaves `_shared/deploy-info.ts` unstamped, so `/health` reports `"version": "dev"` (`selfhost up` stamps the commit). If one function is rejected as too large (the deploy endpoint caps a request at about 5 MB; `api` is the biggest), deploy it with the repo's compacting uploader, which also stamps the commit:

```bash
SUPABASE_PROJECT_REF=<your-ref> SUPABASE_ACCESS_TOKEN=sbp_... node scripts/deploy-edge-function.mjs api
```

Always set `SUPABASE_PROJECT_REF`: without it the script targets Mushi Mushi Cloud.

## 5. Check it

```bash
curl https://<your-ref>.supabase.co/functions/v1/api/health        # {"status":"ok","mode":"self-hosted",…}
curl https://<your-ref>.supabase.co/functions/v1/api/health/ready  # database reachable
npx mushi-mushi@latest selfhost doctor
```

In SQL:

```sql
-- Cron jobs reach your project, not Mushi Mushi Cloud
select key, case when key = 'supabase_url' then value else '(set)' end
  from mushi_runtime_config
 where key in ('supabase_url', 'service_role_key', 'internal_caller_token');

-- Pipeline recovery: success or degraded, not skipped
select status, metadata from cron_runs
 where job_name = 'pipeline-recovery' order by finished_at desc limit 3;

-- Tables with RLS disabled (should return no rows)
select * from mushi_rls_coverage_snapshot() where not rls_enabled;
```

Then serve the console: [Host the console](/self-hosting/admin-spa).

## Row-level security

Every table ships with RLS on and project-scoped policies. The edge functions use the service-role client, which bypasses RLS, so a custom function or route must always scope its queries by `project_id`. Policies use the subquery form, evaluated once per query instead of once per row:

```sql
create policy "users see own project data"
on public.reports for select
using (project_id in (
  select project_id from public.project_members
  where user_id = (select auth.uid())
));
```
